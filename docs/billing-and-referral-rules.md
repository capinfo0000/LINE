# 料金・紹介特典・LINE運用の決まりごと

このファイルは「なぜそうなっているか」を残すためのものです。
コードを読めば「どうなっているか」は分かりますが、**なぜその線引きにしたか**は
残らないので、判断の理由をここに書いています。

会員に見せる説明は `public/pricing.php`（`/pricing`）にあり、
そちらが正式な案内文です。数値はすべて設定から引いているので、
このファイルの数字は「既定値のときの例」として読んでください。

---

## 1. 料金のフェーズ

| フェーズ | 条件 | 会員から見た状態 |
|---|---|---|
| 無料フェーズ | カウント対象が上限（既定100名）以下 | 全機能が無料 |
| 猶予期間 | 上限を超えた〜その月の末日 | まだ無料。有料にするかを**会員が選ぶ時期** |
| 課金フェーズ | 超えた月の翌月1日から | 月額会費（既定 税込500円）が必要 |

- 判定は `billing_reached_at()` / `billing_starts_at()` / `billing_started()` /
  `billing_grace_active()`（`src/payment.php`）
- **`billing_reached_at()` は読み取り時に到達を確定させて `app_settings` に書く。**
  cron が最初の到達者になることもあるが、それは意図した挙動（誰かがアクセスした
  時点で確定させたい／cron に依存させたくない）
- **「先着◯名」に数えるのは自己紹介が入った会員だけ**（`counted_member_count()`）。
  IDを発行しただけの人を含めると、無料枠が実態より早く埋まってしまう

### 払わなかった人

**退会にはならない。** 会員のままで、使えなくなるのは「さがす」だけ
（`member_requires_subscription()` / `member_search_locked()`）。
プロフィールの編集・公開・共有URL・おすすめ・ポイントはそのまま使える。

### 猶予期間に申し込んだ人の初回請求

**課金開始日（翌月1日）から。** Stripe の `trial_end` で先送りする
（`subscription_trial_end()`）。これが無いと「猶予期間は無料」と案内しながら、
早く決めた人ほど多く払うことになる。

**Stripe は `trial_end` が約48時間より先でないと受け付けない。**
月末ぎりぎりに到達して猶予が短いときは付けず、画面の文言も出し分ける。

### `trialing` を持ち込まない

`trial_end` を使うと Stripe は `trialing` を返す。だがアプリは「有効な契約か」を
`subscription_status === 'active'` で判定している箇所が多く（ロック判定・紹介の
カウント・プラン・一覧の並び）、`trialing` を保存すると全部が「未契約」に倒れる。
**`handle_subscription_status()` で `trialing` を受けたら `active` として保存する。**

## 2. 紹介特典（2段階）

| 段階 | 条件 | 取り消し |
|---|---|---|
| 通常の無料 | 紹介した相手のうち**契約中が5名以上** | **あり。** 5名を割ると**翌月から**通常額 |
| 永久無料 | その5名が**それぞれ5名以上**紹介（＝下に25名） | **なし** |

- しきい値は `referral_waiver_min()`（既定5）。「5名**以上**」で成立する
- 判定は `evaluate_referral_waiver()`。cron の `waiver` ジョブで動く
- 永久無料の資格は `members.waiver_earned_at` に記録する。
  `subscription_waived`（＝いま Stripe 側にクーポンが付いているか）とは**別の列**。
  混ぜると `apply/remove_subscription_waiver()` の冪等ガードが壊れる

### 数え方

- 数えるのは `subscription_status = 'active'` の紹介先。
  **抜けるのは完全に解約した人だけ**
- **紹介したあとにその人自身が無料化されても、人数に残り続ける**（契約は続いている）。
  これがA案。`referral_waiver_mode()` を B に切り替えると「実際に払っている人だけ」に絞られる
- 5名を割ったあと、**解約した本人が戻らなくても、新しく誰かを紹介して
  その人が契約すれば**5名に戻って再び無料になる
- 紹介コードの登録は1人1回だけ。あとから変更・取り消しはできない
  （`has_referrer()` ＋ `referrals.joiner_id` の UNIQUE）

### 「翌月から」は自動でそうなる

クーポンを外しても当月分は請求済み（0円）のままなので、通常額になるのは
次回の請求から。日割りの調整はしていない。

### 無料が外れたら本人に知らせる

`notify_waiver_lost()` が公式LINE（未連携ならメール）で1通送る。
「無料です」と案内していた人が翌月いきなり請求されると必ず問い合わせになるため。

cron は毎日回るので、`members.waiver_lost_notified_at` で1回に絞っている
（claim-first）。**送信に完全に失敗したら列を戻して次回に再試行する。**
claim を先にするのは、途中で落ちたときに二重送信するより無音のほうがマシなため。
無料に戻ったら列を NULL に戻し、次に外れたときまた送れるようにする。

### 不正への備え

`record_referral()` は自己紹介を弾くが、同一人物の別アカウントは防げない。
ただし**相手が実際に契約しないと数に入らない**ので、タダで水増しはできない。
発覚したときは会員詳細から個別に剥奪する（`revoke_member_waiver()`）。
無料比率は運営ダッシュボードで監視できる。

**B案に切り替えても、すでに永久無料を達成した会員の無料は外れない。**
効くのはこれから達成する人だけ。

## 3. 公式LINEの運用（初期運用）

`signup_mode()` が `'auto'`（既定）のときの流れ。

### 友だち追加 → 1通で完結

`line_welcome_text()` が、次を**1通**にまとめて返す。

サービスの説明／ログイン情報（URL・ID・仮パスワード）／はじめにやること／
料金／説明会の案内／交流用オープンチャット。

**1通にまとめているのは通数を消費しないため。**
返信（`line_reply()`）は公式LINEの無料枠を消費しないが、
push（`line_push()`）は宛先1件につき1通消費する。
以前は挨拶を返信、ID/PWを push で別送りしていたので、友だち1人につき1通減っていた。

そのため `provision_free_member_from_contact($userId, false)` と呼び、
**送らせずに資格情報を受け取って**返信に載せている。
送らない場合も配布済みフラグ（`credentials_sent`）はそこで消費する
（あとで別経路が二重に push しないため）。

### 友だち追加をやり直した人

`line_contacts` の行は残るので、そのままだと新規発行の経路に入らず
挨拶だけが届く。`reissue_credentials_if_never_used()` で仮パスワードを作り直して
1通に載せる。

**すでにご自身のパスワードへ変更済みの人には何もしない。**
作り直すと、いま使えているパスワードが使えなくなってしまうため。
その場合はログイン情報の段落を落として、会員サイトの案内だけにする。

### 説明会

**希望者だけが申し込む。**トークに「説明会」と送ると日程のカルーセルが出る
（`src/line.php` のキーワード応答）。「面談」で個別面談。
それ以外のテキストにはクイックリプライのメニューが返る。
枠が0件でも落ちず、「現在ご案内できる日程がありません」に差し替わる。

枠は運営画面の「説明会」で作る。Zoom の会議は**枠の作成時に1つ発行して共有**する
（申込者ごとに別会議ができる事故を防ぐため）。

### 決済はLINEで送らない

**決済は会員サイトの中だけで行う。**
以前は承認時に `/checkout` のリンクを push していたが、その経路は
`create_subscription_checkout()` を通らず、**初回請求の先送りも紹介特典の
クーポンも付かなかった。**猶予期間にその経路で入った人だけが不利になるため、
経路ごと削除した（`public/checkout.php` も削除）。

運営が個別に手を貸す「決済リンクを発行」（会員詳細）は残している。
こちらは `create_subscription_checkout()` を通るので条件が正しく付く。

## 4. プラン（松竹梅は見送り中）

いまは有料プラン1つだけで運用している。

`member_plan()` は**有効な契約があれば premium** を返す。つまり
「ベーシック」は課金フェーズで契約していない人だけになり、その人は
「さがす」ごとロックされる。結果として**ベーシック向けの制限UI
（検索条件の絞り込み・おすすめの表示上限）は現在表示されない。**
3段階のプランを入れたときに効くようになる。

## 5. 広告

- 枠は3つ（`ad_slots()`）… PCの左右（side）／一覧の中（feed）／タブバーの上（bar）
- 運営画面からON/OFFできる。**画像が無い枠は何も表示しない**
- 追加料金で非表示にできる（`member/adfree.php`）。**買い切り**にしてある。
  2つ目のサブスクにすると Webhook の受け口が会費と混ざって危ないため
- 広告は自前でホストする。**AdSense を入れるなら CSP の変更が必要**

## 6. cron（登録しないと動かないもの）

```
https://<ドメイン>/cron?job=<job>&token=<CRON_TOKEN>
```

| job | 用途 | 頻度の目安 |
|---|---|---|
| `waiver` | **紹介特典の判定・付け外し・通知** | 1日1回 |
| `remind` | 予約のリマインド | 1時間ごと |
| `reconcile` | 決済の取りこぼし救済 | 1日1回 |
| `recommend` | おすすめの再計算 | 1日1回 |

**`waiver` が登録されていないと、5名達成しても無料になりませんし、
5名を割っても解除も通知も起きません。**

Web版とCLI版でロックファイルが別（`cron_waiver.lock` / `waiver.lock`）なので、
**どちらか一方だけを登録すること。**両方だと排他が効かない。

## 7. 引き継ぎ時に気をつけること

### デプロイ

- CoreServer V2 のフラット配置。プロジェクト全体を `public_html` に置き、
  ルートの `.htaccess` が `^(.*)$ → public/$1` に書き換える
- **本番の運営フォルダ名は `public/admin` ではない**（推測されないよう改名してある）。
  デプロイ用のZIPを作るときは必ず改名する
- **mod_rewrite の規則は、子の `.htaccess` が `RewriteEngine On` を宣言すると
  継承されない。**`/public/` の規則は両方の `.htaccess` に必要
- ZIPに入れてはいけないもの … `.env` / `vendor/` / `*.sqlite` / `public/uploads/` /
  `data/` / `install.php`

### 直したことのある落とし穴

- **SQLite の型比較**：PDO は既定でプレースホルダを文字列としてバインドし、
  SQLite は「数値 < 文字列」で型どうしを比較する。そのため `COUNT(*) >= ?` が
  **常に偽**になる。しきい値は `PDO::PARAM_INT` で明示的に渡す
  （`count_qualified_referrals()`）
- **CSPが厳しい**。インラインJSは禁止（`onclick` は使えない）。
  `data-*` 属性＋`app.js` のイベント委譲で書く
- **CSSの詳細度**：`.ad--bar img` と `.ad img` は同じ詳細度なので、
  記述順で決まる
- **`session.gc_probability = 0`** のホストなので PHP がセッションを掃除しない。
  `session_files_cleanup()` を自前で呼んでいる
- **Stripeの無料化クーポンは `duration: 'forever'`**。外さなければ無料が続く

### まだ無いもの

- **予約のキャンセル導線**。`set_booking_status()`（`src/booking.php`）は
  実装済みだが呼び出し元が1つも無い。ドタキャンした席が開催時刻まで
  塞がったままになる。説明会を続けるなら早めに要る
