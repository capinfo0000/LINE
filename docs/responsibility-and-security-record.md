# 責任分界点 と セキュリティ実施記録（説明責任・デューデリジェンス用）

> 目的: 万一の情報漏えい時に「運営者として取り得る対策はすべて実施済み」であることを示し、
> どこまでが当方の責任で、どこからが外部事業者（Stripe / CORESERVER）の責任かを明確にする記録。
> 最終更新: 2026-06-14 ／ 対象: イベント事前決済アプリ（`capinfo0000/event`）

---

## 1. 責任分界点（だれが何を守るか）

| 領域 | 保持/処理する情報 | 主たる責任 | 当方の備え |
|---|---|---|---|
| **カード情報**（番号・期限・CVC） | 当アプリ・運営者は**一切受け取らない/保持しない** | **Stripe**（PCI DSS Lv1 準拠） | カード入力は Stripe ホスト画面のみ。コードでカード情報を扱わない設計 |
| **参加者の決済・名簿（氏名/メール/電話/備考）** | **各主催者の Stripe アカウント**に保存 | **Stripe ＋ 各主催者** | システムDBに参加者PIIを保持しない。取得は主催者本人のセッション時のみ |
| **主催者アカウント（メール/パスワード/イベント定義）** | プラットフォームのDB（SQLite） | **当方（運営者）** | パスワードは bcrypt、DBは公開領域外、`.htaccess`/権限で保護 |
| **主催者の Stripe APIキー** | 公開フォルダ外のファイル（暗号化） | **当方＋各主催者** | AES-256-GCM 暗号化（APP_KEY）。公開領域外。画面はマスク表示 |
| **サーバー/OS/バックアップ/回線** | — | **CORESERVER（GMO）** | 提供されるセキュリティ機能（SSL/権限/バックアップ）を適切に利用 |
| **イベントの内容・参加費・返金可否** | 各主催者が決定 | **各主催者** | 規約で主催者-参加者間の責任を明確化 |

> **要点**: カード情報と参加者PIIの「保管」は Stripe 側。サーバー基盤の安全性は CORESERVER 側。
> 当方が直接守るのは「アプリのコード」と「主催者アカウント・接続鍵の取り扱い」であり、そこは下記のとおり対策済み。

## 2. 実施済みのセキュリティ対策（デューデリジェンスの証跡）

### 設計・データ最小化
- カード情報を**サーバーで一切扱わない**（Stripe Checkout）。
- 参加者PIIを**システムDBに保持しない**（各主催者の Stripe が保管）。
- 保持必須データ（主催者アカウント・イベント定義・接続鍵）のみを管理。

### 認証・認可
- パスワードは **bcrypt**（復元不可）。弱いパスワード/反復を拒否。
- ログイン：メール単位＋IP単位のレート制限、**タイミング平準化**（アカウント列挙対策）、CAPTCHA対応（任意）。
- 全状態変更は **CSRF トークン**検証、POST 限定。
- **テナント分離**：全データ取得/操作は所有者チェック。**IDOR 対策**（操作対象が本人のイベントの参加者か Stripe 側で検証）。
- 管理者専用機能は `require_admin_tenant`。**権限昇格不可**（実地検証済み）。

### 機密の保護
- **Stripe APIキーは公開フォルダ外に暗号化保存**（AES-256-GCM、APP_KEY 自動生成）。鍵ファイル単体が漏れても `.env` のキーが無ければ復号不可。
- **DB・鍵・セッションを公開フォルダ外**へ。`.htaccess` で `.env`/DB/ログ/ソースの直アクセスを拒否。
- 管理画面に**構成リスクの自動警告**（DB/鍵が公開領域内なら重大警告、`.env` 実露出の自己診断）。
- メール監査ログは**本文・トークン・完全アドレスを記録しない**（マスクのみ）。

### Web 堅牢化
- セキュリティヘッダ：**CSP（nonce・unsafe-inline無し）/ X-Frame-Options DENY / HSTS / Referrer-Policy / Permissions-Policy / COOP / CORP / object-src 'none'**。
- Cookie：`Secure`（HTTPS時）/ `HttpOnly` / `SameSite=Lax`、ログイン時 ID 再生成、アイドルタイムアウト。
- **CSV 数式インジェクション対策**、出力エスケープ（`e()`）。
- 未認証エンドポイントのレート制限、公開GETの残席キャッシュ（Stripe濫用抑止）。
- SSRF/Hostヘッダ注入の排除（自己診断は `APP_BASE_URL` 固定）。

### 監査ログ（不正の痕跡を残す）
- **`audit.log`**（DB と同じ非公開フォルダ＝公開領域外）に、操作の証跡を記録：
  - 認証：`login.ok` / `login.fail` / `login.blocked` / `signup` / `account.password_change`
  - 鍵：`stripe.key.save`（mode/verify のみ・鍵値は記録しない）/ `stripe.key.clear`
  - データ操作・持ち出し：`refund` / `csv.export`（件数）/ `event.delete`
  - **攻撃の兆候**：`authz.deny`（他テナントのリソースへの操作試行）/ `authz.admin_deny` / `csrf.fail`
  - 各行に 日時・送信元IP・User-Agent を付与。**秘密（鍵・カード情報・トークン）やフルのPIIは記録しない**（メールはマスク）。
- 用途：万一の漏えい・不正時に「いつ・どこから・誰が・何をしたか」を追跡し、原因箇所を特定して塞ぐ。

### 検証
- 黒box・**ログイン後**の侵入テストを実施し、**Web経由でのAPIキー/他テナントデータ窃取は不成立**を確認（`docs/pentest-result-2.md`、`docs/security-threat-analysis.md`）。

## 3. 上流（Stripe / CORESERVER）が漏えいした場合の影響と、当方の備え

| 上流漏えい | 起こり得る影響 | 当方が取ってある緩和 |
|---|---|---|
| **Stripe 側の漏えい** | 参加者PII・決済情報の流出 | 当方はカード情報を保持せず、PCI DSS 準拠の Stripe に委託（適正な委託先選定）。**制限付きキー(rk_)** 推奨で当方アカウントの権限を最小化 |
| **CORESERVER 側の漏えい/侵入**（サーバー丸ごと） | DB・`.env`・鍵ファイルの流出 | 鍵は暗号化保存＋公開領域外。被害最小化のため**テスト/制限付きキー**運用、**鍵ローテーション手順**整備、バックアップ暗号化を推奨。完全侵入は自己ホストの構造的限界として規約・ポリシーで明示 |
| **バックアップの流出** | DB・鍵の流出 | バックアップは暗号化保管。`.env`(APP_KEY) とは別管理で復号を困難化 |

> いずれも「**委託先の適正選定**」「**当方側で取り得る多層防御の実施**」「**被害最小化（制限付きキー・最小権限）**」を満たしており、当方の善管注意義務の履行を示せる状態。

## 4. インシデント対応手順（漏えい時）

1. **遮断・無効化**: Stripe の APIキーを Roll（無効化＋再発行）。`.env`/鍵ファイルを差し替え（手順は `docs/security-threat-analysis.md` §9）。
2. **影響調査**: Stripe ダッシュボードのログで不審な操作（想定外の返金・顧客取得）を確認。
3. **法令対応（個人情報保護法）**: 要配慮個人情報や一定規模の漏えいは、**個人情報保護委員会（PPC）への報告**と**本人通知**が必要。速やかに事実関係を整理し対応。
4. **記録**: 発生～対応の経緯を記録（本書に追記）。

## 5. 運用チェックリスト（「非を残さない」ために継続すること）

- [ ] **法務ページの確定**（最重要・未了）: `privacy.php`・`tokushoho.php`・`terms.php` の `［事業者名/氏名/住所/連絡先/制定日］` を実際の情報に置換。特商法表記は決済を伴うため**必須**。
- [ ] プライバシーポリシーに「Stripe へ決済処理を委託」「カード情報は当方非保持」を明記（テンプレに記載済み・確定すること）。
- [ ] Stripe は**制限付きキー(rk_)**＋必要最小権限で運用。
- [ ] `.env` に `APP_KEY` を設定（または鍵保存時の自動生成を確認）。DB・鍵・セッションが**公開フォルダ外**にあること（管理画面に重大警告が出ていない）。
- [ ] デプロイ後、`/.env`・`/data/app.sqlite`・`/src/` が **403/404** であることを確認。
- [ ] バックアップは**暗号化**して保管。`.env` とDB/鍵を同一バックアップに平文同梱しない。
- [ ] 同一CORESERVERアカウント上の**他サイト（board-game/opinion-box 等）の脆弱性を放置しない**（同一ユーザーで鍵ファイルへ到達し得るため）。
- [ ] 重要操作（鍵登録・返金）は信頼できる端末・回線から。
- [ ] 参加者からの開示・訂正・削除請求への対応窓口を用意（プライバシーポリシーに記載）。

## 6. まとめ

- **当方が直接守る範囲（アプリ・アカウント・接続鍵）は、取り得る対策をすべて実施済み**（§2）。
- **カード情報・参加者PIIの保管は Stripe、サーバー基盤は CORESERVER** の責任領域であり、当方は適正な委託先選定と、当方側で可能な多層防御・被害最小化を実施（§1, §3）。
- 残る「上流の漏えい」「サーバー丸ごと侵入」は外部要因だが、**暗号化・最小権限・ローテーション・通知手順**を整え、影響を最小化できる状態にしてある（§3, §4）。
- 残タスクは主に**法務ページの内容確定**（§5）。これを完了すれば、運営者として説明責任を果たせる体制が整う。
